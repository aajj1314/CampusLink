# 01 · 模块职责

> 原则：每个模块有明确的"不做什么"。跨模块的东西（协议、数据结构）只在 `02/03` 定义一次。

## 1. CampusLink Router（OpenWrt，控制面）

**定位**：唯一持有 Portal 会话的节点；认证的决策者与编排者；视觉任务的分发者。

| 职责 | 说明 | 复用自现有代码 |
|---|---|---|
| Portal 会话管理 | 会话创建、Cookie 保管（内存）、失效检测、重认证 | `core/portal.py` 原样复用 |
| 网络状态检测 | generate_204 探测、门户发现、网关读取 | `core/netdetect.py` 原样复用（已含 Linux 分支） |
| 认证编排 | 重试、验证码去重、取消 | `core/authenticator.py` **唯一改动点**：OCR 调用改走 `OcrBackend` |
| 验证码任务生成 | 拿到验证码图片 → 创建任务 → 等结果 | 新增（`taskmanager.py`） |
| 任务生命周期 | pending/assigned/submitted/verified/expired/cancelled、TTL、幂等 | 新增 |
| 结果提交 | 校验 nonce → 交给认证编排 | 新增 |
| 认证状态查询 | 给 Desktop/Mobile 的 UI 提供 `/auth/status` | 新增（包装 `netdetect` + 会话状态） |
| 设备与配对管理 | PIN 签发、token 校验、吊销 | 新增（`pairing.py`） |
| API 服务 | `/api/v1` 全部端点 | 新增（`apiserver.py`） |

**明确不做**：
- **不做 OCR**（Vision Lite 立项前）——`core/ocr.py` 及其依赖不安装到 Router
- **不持久化 Cookie / 密码到 flash**——Cookie 在内存；密码沿用 keyring 的思路在 OpenWrt 上不可用，改为：配置文件存账号（明文账号、**不存密码**），密码每次启动由用户通过 Desktop/Mobile 下发一次并保存在内存，或存 root-only 权限的内存文件
- **不做图形界面**——LuCI 集成不做（成本高收益低），管理全走 Desktop/Mobile
- **不做 UPnP / 端口转发**——API 只监听 LAN

**实现形态**（设计倾向，非本阶段承诺）：单个 Python 3 进程 + `http.server`/`aiohttp` 之一，OpenWrt init 脚本托管；依赖 vendoring 打成一个 `.ipk` 或 `/opt` 目录。

## 2. CampusLink Desktop（Windows，视觉面 + 兼容面）

**定位**：现有稳定版**不动**；新增一个可选的"视觉节点"角色。

| 职责 | 说明 |
|---|---|
| 现有全部功能 | 独立模式的 GUI 认证、托盘、自启、断线重连——**保持现状，不重构** |
| Vision API 节点（新增，默认关闭） | 连接 Router → 配对 → 长轮询领任务 → 用现有 `core/ocr.py` 识别 → 提交结果 |
| 降级决策 | 监测 Router 可达性；Router 托管模式下**禁用自己的认证动作**（避免双登录抢并发），Router 失联 N 秒后恢复独立模式 |
| 状态展示 | Router 模式下主窗口显示"由 Router 托管 / 节点在线" |

**明确不做**：
- 不把 Router 的 Cookie 拉到本地（没有意义，IP 不匹配）
- 不在 Router 模式下修改门户配置（配置单一来源在 Router）
- 视觉节点功能**不改变**现有 GUI 的任何默认行为（默认关闭，开关在设置里）

**改动边界**：全部新增代码放 `campuslink/visionnode/` 新包 + `main_window` 加一个设置区；`core/` 只加 `OcrBackend` 抽象（见 03 文档），不改既有行为。

## 3. CampusLink Mobile（Android，视觉面 + 人工兜底）

**定位**：轻量视觉节点；**人工输入是它的独特价值**——Desktop 识别失败时，手机人工看图输字比"反复重试"更快。

| 职责 | 说明 |
|---|---|
| 连接与配对 | mDNS 发现或手输 IP → PIN 配对 |
| 获取任务 | 长轮询 `/vision/tasks/next` |
| OpenCV 本地处理 | opencv-android + onnxruntime-mobile 加载同一 ONNX 模型（与 Desktop 共享模型文件，版本一起管理） |
| 人工输入 | 任务带 `allow_manual` 标记时，展示原图 + 输入框；这是 Mobile 的默认交互 |
| 提交结果 | 带 nonce 幂等提交 |
| 状态查看 | 只读：当前网络状态、最近认证结果（**不含 Cookie、不含密码**） |

**明确不做**：
- 不做桌面端功能复刻（不做 GUI 认证入口）
- 不缓存验证码图片到相册/外部存储
- 不做后台常驻保活（Android 杀后台是常态；设计上节点掉线不影响 Router，任务超时转给其它节点或人工）

**技术选型倾向**（设计倾向，Phase 3 定稿）：Kotlin + OkHttp + `opencv-android`；OCR 用 onnxruntime-mobile 跑同一个 13 MB 模型。APK 增量预计 ~55 MB。

## 4. CampusLink Vision Lite（预研课题）

**定位**：不是产品模块，是一个有明确立项门槛的研究课题（见 00 文档 §5）。

| 阶段 | 内容 | 门槛 |
|---|---|---|
| L1 数据采集 | Router 侧采 200+ 张真实验证码（复用现有 `collect.py` 思路） | — |
| L2 经典 CV 原型 | 阈值 → 连通域切分 → 逐字符模板匹配；PC 上先验证算法 | 切分准确率 ≥ 98% |
| L3 MIPS 移植评估 | 用 C 重写热路径，交叉编译，实测 RSS 与耗时 | RSS 增量 ≤ 15 MB 且单张 ≤ 3 s |
| L4 识别率验收 | 全流程在 Router 上跑 | **识别率 ≥ 95% 才立项，否则放弃** |

**明确不做**：不在 Router 上引入任何深度学习运行时；不为此维护标注团队（模板库来自自动采集 + 人工核对一次性建立）。

## 5. 跨模块职责矩阵

| 能力 | Router | Desktop | Mobile |
|---|---|---|---|
| 持有 Portal Cookie | ✅ 唯一 | ❌ | ❌ |
| 发起 Portal 认证 | ✅ | 仅独立模式 | ❌ |
| 执行 OCR | 预研 | ✅ | ✅（或人工） |
| 人工输入验证码 | — | ❌（无意义，PC 上直接看） | ✅ |
| 修改门户配置 | ✅ 唯一 | 仅独立模式 | ❌ 只读 |
| 查看认证状态 | 提供 API | ✅ | ✅ 只读 |
| 设备配对/吊销 | ✅ 唯一 | 自助配对 | 自助配对 |
