# 云端 OCR 方案评估（2026-11-19）

> 结论：**不采用**。本文记录实测数据，避免以后重复评估。

## 背景

用户提出：把超算互联网的 OCR API（`https://api.scnet.cn/api/llm/v1/ocr/recognize`）
作为注销验证码识别的首选项，本地 ddddocr 作兜底。理由是「云端更快更准」。

## 实测方法

1. 用 3 张已知答案的历史样本做初步对比
2. 从真实注销页抓 8 张验证码，**用实际提交验证对错**（不靠人工判断）
3. 分别测两者的延迟

## 实测结果

### 准确率：本地 7/8，云端 0/8

| # | 本地 ddddocr | 云端 API | API 置信度 | 谁对 |
|---|---|---|---|---|
| 1 | `hr8x` | `H8X1` | 0.50 | 本地 |
| 2 | `x2s` | `X` | 0.00 | 都错 |
| 3 | `sp4a` | `SP<` | 0.67 | 本地 |
| 4 | `gaxk` | `K` | 0.00 | 本地 |
| 5 | `spj2` | `SPJ2` | 1.00 | 本地 |
| 6 | `y58c` | `Y58` | 0.50 | 本地 |
| 7 | `5g55` | `--` | 0.00 | 本地 |
| 8 | `y5l3` | `子` | 0.00 | 本地 |

云端 API 的典型失败形态：
- **漏字符**（`spj2` → `SPJ2`，置信度 1.0 但少了 `a`）
- **只认出一个字符**（`gaxk` → `K`，`x2s` → `X`）
- **识别成汉字**（`y5l3` → `子`）
- **完全失败**（`5g55` → `--`）

### 延迟：本地快 51 倍

| | 平均 | 范围 |
|---|---|---|
| 本地 ddddocr | **11.2 ms** | 10.0 ~ 12.3 |
| 云端 API | **575 ms** | 514 ~ 1789 |

## 为什么云端反而不行

该 API 的 `ocrType=GENERAL` 是**文档 OCR**，不是验证码识别：

1. **做版面分析**：返回结构里有 `angle`（旋转角度检测）、`anglenet_class`、
   `text_class`（文本分类）、`cutIndex`（切块索引）——
   它在判断「这是一段什么文字」，而不是「这几个字符是什么」

2. **对小图判定为"非文本"**：返回 `confidence=0.0` 的那些，
   `elements.text` 直接是空数组或单个字符 —— 它认为这不是有效文本行

3. **尺寸不匹配**：验证码是 80×24，返回的 `width=81`、`height=31`，
   `text_class='2'`（分类为「其他」）

4. **会漏字**：即使置信度 1.0（`spj2` → `SPJ2`），也少了 `a`。
   说明它做了某种后处理（可能是语言模型纠错），对随机字母数字有害

## 场景性质对比

| | 验证码识别 | 文档 OCR |
|---|---|---|
| 图像 | 80×24，4 个随机字符 | A4 扫描件，成段文字 |
| 要求 | 毫秒级、高准确 | 可等待秒级、要版面结构 |
| 频率 | 每次注销/登录都调 | 偶发 |

**结论：这是两个不同的任务，用文档 OCR 做验证码是方向错了。**

## 顺带测到的其他事实

- 端点需要 `ocrType=GENERAL`（**全大写**）。`general` / `text` / `captcha`
  都返回 400 `ocr_type not support`
- 成功响应里 `code="0"`，结果在 `data[0].result[0]`，
  文本在 `elements.text[]` 数组里，需要拼接
- 云端会**把上传的图片存到自己的 COS**（返回 `cosPath`）——
  验证码图片虽不敏感，但这是个隐私考虑点

## 如果将来要重新评估

前提变了才值得重测：
- API 提供了 `ocrType=CAPTCHA` 之类的专用模式
- 换成了专门做验证码的服务（如 ddddocr 的商业版、capsolver 之类）
- 本地识别率明显下降到不可接受

重测方法：直接跑本文的对照脚本（抓真实图 + 实际提交验证），
**不要只对比识别结果**——必须用「提交后是否返回验证码错误」作为判据，
因为人工比对容易忽略细微的字符差异。
