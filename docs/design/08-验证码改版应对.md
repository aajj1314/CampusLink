# 08 · 验证码改版应对（字符型 → 算式型）

> 触发时间：2026-10-17
> 触发方式：用户提供真实登录页截图，截图标签由「验证码」变为「验证码：输入计算结果」
> 影响范围：`campuslink/core/`（OCR 与认证链路）、`campuslink/profiles/桂林信息科技学院.json`
> 不影响：`campuslink/router/**`（控制面只负责转发图片，不关心答案怎么来的）、`docs/design/02`、`docs/design/03`

---

## 1. 到底变了什么

改版前，验证码是 4 位随机字母数字，OCR 认出字符后**原样提交**。

改版后，验证码是一道**算术题**，要求填写**计算结果**。实测 30 张真实样本，运算符集合为：

| 运算符 | 出现形式 | 示例 | 答案 |
|---|---|---|---|
| 加 | 汉字 `加` | `7加9=?` | 16 |
| 乘 | 汉字 `乘` | `9乘8=?` | 72 |
| 除 | 符号 `÷` | `28÷4=?` | 7 |
| 减 | 符号 `-`（待确认） | `57-0=?` | 57 |

格式固定为 `A <运算符> B = ?`，其中：

- **A**：1~2 位（0~98）
- **B**：**加/乘/除恒为 1 位；减法的 B 有 64.4% 是 2 位**
- 尾部 `=?` 是固定的求值标记

验证码图片取自 `http://10.6.6.6/ACaptcha.ashx`，**200×60 PNG**。

> **2026-10-19 修正（原文档此处写"B 恒为 1 位"，是错的）**
>
> 当时只有 30 张样本，减法的两位 B 恰好一张都没抽到。用 3187 条标注统计后：
>
> | 运算符 | 样本 | B 为 1 位 | B 为 2 位 | B2 占比 |
> |---|---|---|---|---|
> | 加 | 741 | 741 | 0 | 0.0% |
> | 乘 | 786 | 786 | 0 | 0.0% |
> | 除 | 840 | 840 | 0 | 0.0% |
> | **减** | **820** | 292 | **528** | **64.4%** |
>
> 也就是说：**减法需要两个量级相近的数才有意义**（`55减23`），
> 其余三种运算的第二操作数都是单个数位。
>
> 这条修正有直接后果：`ocr.py` 的启发式链路目前传 `max_b_digits=1`，
> 它会把减法里 64.4% 的题截断成一位（`55减23`→`55减2`，答案从 32 变 53）。
> **这是当前版本的已知缺陷，见 §5.1。**
>
> 另外两个同样被推翻的先验（一并记下，勿再按旧规律"修正"标注）：
> - 减法**结果可以为负**（53/820 = 6.5%，如 `1减8=?`）
> - 除法**可以不整除**（56/840 = 6.7%，如 `2除7=?`）

## 2. 原链路为什么必然失败（不是识别率下降）

原链路有两处硬假设同时失效：

**其一，`core/ocr.py` 的白名单会整条丢弃结果。**

```python
CHAR_RE = re.compile(r"^[0-9A-Za-z]+$")     # 只要出现运算符就判为幻觉
```

`7加9=?` 识别出来是 `7加9`，含汉字 `加` → 不能通过 `CHAR_RE` → 该策略的结果被丢弃。
所有策略都丢弃后 `recognize()` 返回空串 → `Authenticator` 打「验证码没认出来」→
重试 4 次全空 → 抛 `CaptchaFailed`「验证码识别失败，请稍后重试」。

实测（用用户截图里那张验证码原样裁剪后喂给旧链路）：

```
ddddocr 输出: '神2'
CHAR_RE 校验: 不通过
```

**其二，`build_payload()` 把识别文本原样当答案提交，没有"算"这一步。**

即使白名单放开、成功认出 `7加9=?`，提交上去的是字符串 `7加9`，而门户要的是 `16`。

## 3. 改造方案

### 3.1 新增纯逻辑层 `campuslink/core/captcha_math.py`

只做「文本 → 解析 → 计算」，不碰图像，因此可以脱离 cv2 单独测试（69 条用例）。

- 运算符别名归一化：`加/+/＋` → `+`，`乘/×/x/*` → `*`，`除/÷/／` → `/`，`减/－/—/-` → `-`
- `parse_expression()`：取运算符**左侧最后一段**数字和**右侧最前一段**数字（干扰字会粘在两端）
- `evaluate()`：手写四则运算，**不用 `eval()`** —— 识别结果是外部输入，不能当代码执行入口
- 除法**必须整除**，除不尽返回 `None`（原以为样本里除法全是整数解；2026-10-19 实测 6.7% 的除题除不尽，见 §1 修正 —— 返回 `None` 让它变成"换图"，属安全失败，但会多耗一张图）
- `max_b_digits` 参数：把 B 截到 1 位，专门对付 `=?` 被认成数字。**该参数在减法上会误伤，见 §5.1**

### 3.2 新增识别链路 `core/ocr.recognize_math()`

不改动既有 `recognize()` 一个字节（那是 44 条稳定版测试覆盖的路径）。

关键设计与理由：

| 做法 | 为什么 |
|---|---|
| 用**独立 OCR 实例** + `set_ranges("0123456789加减乘除÷×+-")` | `set_ranges` 是实例级状态，在共享实例上调用会改掉字符型验证码的识别行为。限定字符集后 `和云弈`/`u`/`l` 这类幻觉被彻底挡掉 |
| 前景用「到白色点的欧氏距离」而非亮度/饱和度 | 主字符颜色随机（深青、深蓝、深紫、灰都有），HSV 跨度极大，共同特征只有"离白很远" |
| 逐块识别，不做整行识别 | 整行喂 ddddocr 会把 `=?` 当成操作数：`8加4=?` → `'8加42'`，`6乘1=?` → `'6乘79'`，答案必然算错 |
| 多预处理 × 双模型投票，票数 < 2 就返回空串 | **返回空串 = 换一张图**，绝不提交猜出来的答案。猜错要付一次登录尝试的代价 |
| B 只取 1 位 | 样本里 B 恒为 0~9，而尾部 `=?` 极易被认成数字 |

### 3.3 接线

- `PortalProfile.captcha_mode: str = "text"` —— **默认 text，保证既有行为零变化**
- `桂林信息科技学院.json` → `"captcha_mode": "math"`
- `LocalDdddocrBackend(mode=...)`：`text` 走原链路，`math` 走算式求解
- `Authenticator._backend()` 从 profile 读 mode 传入
- `Authenticator` 的 verbose 日志在算式形态下打印 `验证码算式 8加4=? → 填 12`

## 4. 识别率实测（如实记录）

30 张真实样本（2026-10-17 从 `ACaptcha.ashx` 抓取）：

```
解出答案: 9/30
其中正确: 4/30  (13%)
其中错误: 5/30  (17%)   ← 错误比不识别更危险
```

典型错误：

| 图 | 实际 | 识别成 | 算出 |
|---|---|---|---|
| `28÷4=?` | 7 | `284-2`（`÷`→`-`） | 282 |
| `5加0=?` | 5 | `55加02`（A 被污染） | 55 |
| `6乘1=?` | 6 | `6乘79`（`1`→`7`） | 42 |

**结论：这套启发式不足以稳定上线。** 该验证码是抗 OCR 设计的：随机颜色字符、随机倾斜、
**深色细斜线直接穿过字符**（去线必伤字）、细笔画小字干扰。

尝试过但无效的方案（避免后人重走）：

| 方案 | 结果 |
|---|---|
| Hough 直线检测去干扰线 | Canny 把字符笔画也当直线，抹线后 `28÷4=?` 的 `4` 被抹掉 |
| 形态学开运算 + 笔画宽度过滤 | 数字和 `=`/`?` 保留，但**汉字 `乘`/`加` 的细笔画被一起削掉** |
| 中值滤波（3/5） | 改善有限，字符本身重叠导致粘连依旧 |
| `=` 几何特征做锚点 | 30 张里 0 张检出（横线被干扰线打断/粘连） |
| ddddocr `det=True` 目标检测 | 该模型是给滑块点选设计的，框数和位置都不对（30 张里 4 张检出 0 框） |
| 整行识别 + 正则后处理 | 70% 能解出式子，但 `?` 混入操作数导致答案几乎全错 |

## 5. 上线的三个选项（需业务决策）

**A. 自动识别 + 多轮重试（当前实现）**

`max_retry=8`，每次失败换新图。单张成功率约 30%（含 17% 错答率），
8 轮内成功概率约 94%，但**平均会提交 1~2 个错答**。
门户对验证码错误通常只换图不锁号，风险中等。适合没人盯着的时候。

**B. 人工输入（最可靠，推荐先用这个）**

GUI 已有 `captcha_seen` 信号把验证码图片显示到界面。加一个输入框让用户自己填答案，
100% 准确。`Authenticator.login()` 的 `on_captcha` 回调已经是现成的挂点。

**C. 训练专用模型（要 90%+ 只能走这条）**

1. 用 `tools/captcha_sampler.py` 抓 500~1000 张（脚本已提供，只抓图不登录）
2. 人工标注答案（可半自动：先用当前识别器出候选，人工只纠正）
3. 训一个 CRNN + CTC（识别 `A<op>B` 文本，求值仍交给 `captcha_math`）
4. 训好后单独开分支决定怎么接入，**不直接改当前主链路**

数据量估计：`加/乘/减/除` 四类 × 数字 0~9 × 两位 A，约 2000 张能到 95%。

### C 方案的定位（2026-10-17 决定，2026-10-19 更新进度）

**C 是一条独立产品线，不与当前版本合并。**

| 项 | 决定 |
|---|---|
| 训练 | 放在 Linux 机器上做，本机不参与 |
| 训练工程 | `ml/`（自包含，交接文档 `ml/AGENT_BRIEF.md`） |
| 数据集 | **3164 张原图 + 3071 条标注**（另 120 张独立测试集） |
| 训练结果 | **已训练完成**：独立测试集 116 张，答案正确 **92.2%**、错答 **6.9%** |
| **推理侧代码** | **不写进当前仓库**。等错答率降到 3% 以下后，单独开分支做 |

理由：`campuslink/core/**` 现在是 223 条测试护着的稳定基线。把「模型优先 + 启发式降级」
的分支逻辑提前塞进去，会让主链路在模型还不存在时就开始依赖一个新模块，
既增加了回归面，也让「当前版本到底用哪条链路」变得含糊。

**所以现在的状态很干净**：`LocalDdddocrBackend(mode="math")` 只有一条路 ——
`ocr.recognize_math()` 的启发式，行为与本文件第 4 节记录的实测结果一致（13%）。

给 Linux 侧的交付只有一件事：**训练数据 + 训练目标**。训练工程怎么用写在
`ml/AGENT_BRIEF.md`，那边不需要知道 Windows 端怎么接线。

**模型当前未达上线条件的唯一原因**：错答率 6.9% > 3%。
"加置信度阈值"这条最直觉的解法已实测证伪（错答样本的置信度接近 1.000），
详见 `ml/AGENT_BRIEF.md` §6.1。方向应是针对细笔画数字（`1`/`7`）补数据。

### 5.1 已知缺陷：`max_b_digits=1` 在减法上会算错（2026-10-19）

`core/ocr.py` 的启发式链路现在是：

```python
answer = captcha_math.solve(joined, max_b_digits=1)
```

截断 B 的目的，是防止尾部 `=?` 被 OCR 认成数字（`8加4=?` → `'8加42'`）。

但减法的 B 有 **64.4%** 是两位（见 §1）。一旦启发式真的认对了 `55减23`，
截断会把它变成 `55减2`，答案从 **32 变成 53** —— 这是**错答**，不是换图，
违背"宁可不认，不能认错"。

影响面：

| 运算符 | 占比 | B 恒 1 位？ | 截断后果 |
|---|---|---|---|
| 加 | 23.3% | 是 | 无害 |
| 乘 | 24.7% | 是 | 无害 |
| 除 | 26.4% | 是 | 无害 |
| **减** | **25.7%** | **否（64.4% 为 2 位）** | **这 64.4% 的题答案必错** |

折算下来是全部题的 16.6%。但启发式本身只有 13% 正确率，
**实际触发概率远低于 16.6%**，所以这不是当前最痛的点。

三种改法：

| 改法 | 好处 | 坏处 |
|---|---|---|
| A. 直接删掉 `max_b_digits` | 减法正确 | `=?` 污染回归（`8加4` 可能变 `8加42`） |
| B. 按运算符区分：减法不截断，其余仍截断 | 精准 | 减法上 `=?` 仍可能污染（`55减23=?` → `55减234`） |
| C. 不动，等识别方案定稿 | 零风险 | 减法保留系统性错答 |

**处置：暂选 C（不改）。** 理由是这个缺陷只在启发式认出完整减法式时才触发，
而启发式本身马上就要被替换。等"用人工输入兜底还是等模型"这件事定下来，
连同识别链路一起改，避免为一个即将下线的路径单独做一次回归。

> 记录在此的目的：**后来者不要以为 `max_b_digits=1` 是经过验证的正确参数** ——
> 它建立在"B 恒为 1 位"这个已被推翻的先验上。

## 6. 待确认事项

原列的三个问题，用 3187 条标注统计后已有两个可以结案：

| 原问题 | 结论 | 依据 |
|---|---|---|
| 运算符是否包含 `减`？ | **包含**，四类大致均衡 | 加 23.3% / 减 25.7% / 乘 24.7% / 除 26.4% |
| `A` 会到 3 位、`B` 会到 2 位吗？ | A 最多 2 位（1 位 1492 / 2 位 1695）；**B 在减法上有 64.4% 是 2 位** | 同上 |
| 除法除不尽时门户要小数还是整数？ | **仍未确认** | 见下 |

唯一存疑项：**除法除不尽时，门户期望填什么？**

实测 56/840（6.7%）的除法题除不尽（如 `2除7=?`）。可能的情况：

1. 门户自己四舍五入/取整校验 → 我们返回 `None` 会白白换图
2. 门户根本不该出这种题（出题端 bug）→ 返回 `None` 换图是正确行为
3. 门户期望特定格式（如保留两位小数）→ 需要实测才知道

**在拿到实证之前，维持"除不尽就换图"**（安全，不提交错答）。
验证方法：真实登录时遇到除不尽的题，手工输入一个整数/小数试一次，
看门户回显是"验证码错误"还是通过 —— 这需要一次真实登录，得等人工操作。
