# 00 · 总体架构

## 1. 现状盘点（先核对事实，再谈设计）

任务书对现状的几处描述与代码实测有出入，先修正，避免设计建立在错误假设上。

| 任务书假设 | 代码实测 | 影响 |
|---|---|---|
| "认证业务与图像处理能力需要解耦" | **模块级已解耦**：`core/` 无 Qt、无 Windows API（imports 仅 requests/bs4/urllib3/标准库）；`cv2`/`numpy` **只被 `core/ocr.py` 引用** | 不需要大重构；跨设备拆分只需加一个接口 |
| "约 200MB 的 OpenCV 依赖文件夹" | `cv2/` 113 MB（`cv2.pyd` 82 MB + FFmpeg DLL 29 MB），另有 ddddocr 85 MB、onnxruntime 43 MB | 视觉栈总重 ~250 MB，这是 Router 不可行的直接原因 |
| "增加可选 Vision API" | Desktop 已有 GUI + core，缺的只是"把 OCR 暴露成局域网服务"这一层 | 增量开发，不破坏现有功能 |
| （未提及）OCR 调用点分散程度 | **全项目仅 1 处**：`authenticator.py:177` 调 `ocr_mod.recognize()`，189 行调 `confidence()` | 拆分的接缝非常干净 |

**结论：本设计不重写，只在既有解耦上加一个 `OcrBackend` 抽象。**

## 2. 目标架构

```
                    ┌────────────────────────────────────────┐
                    │   Router（小米 AC2100 / OpenWrt）        │
                    │   控制面：唯一持有 Portal 会话             │
                    │                                        │
                    │  ┌────────────┐  ┌──────────────────┐  │
                    │  │ 认证引擎     │  │ 任务管理器         │  │
                    │  │ core/portal │→ │ 创建/分发/收结果    │  │
                    │  │ core/netdet │  │ 生命周期/TTL/幂等  │  │
                    │  └─────┬──────┘  └────────┬─────────┘  │
                    │        │ 会话/Cookie 只在这里 │           │
                    │  ┌─────▼──────────────────▼─────────┐  │
                    │  │   HTTP JSON API  /api/v1  (LAN)  │  │
                    │  └───┬──────────────────────┬───────┘  │
                    └──────┼──────────────────────┼──────────┘
                           │ 任务/图像/结果          │ 状态查询
              ┌────────────▼─────────┐   ┌────────▼─────────┐
              │ Desktop（Windows）    │   │ Mobile（Android） │
              │ 视觉面：现有 OCR 算法   │   │ 视觉面：OpenCV 或  │
              │ 兼容面：可独立直连门户  │   │ 人工输入兜底       │
              └──────────────────────┘   └──────────────────┘
```

三种运行模式：

| 模式 | 认证发生在哪 | OCR 发生在哪 | 什么时候用 |
|---|---|---|---|
| **独立模式**（现状） | PC | PC | 没有 Router，或 Router 不可用 |
| **Router 托管模式**（新增） | Router | Desktop / Mobile（可配） | 家里/宿舍多设备，统一由 Router 管理 |
| **Router + 本地 OCR**（远期） | Router | Router（Vision Lite） | 研究课题，见 §5 |

**降级路径是显式设计的**：Router 不可达时，Desktop 自动回退独立模式（检测 `/health` 连续失败即切回），不出现"两头都登录同一个账号"的竞争。

## 3. 核心设计决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **Router 是唯一会话持有者**，Cookie 只在其进程内存 | 任务书要求；且门户会话按 IP 绑定，Router 认证 = Router WAN IP 通过认证，Cookie 给别的节点毫无意义还泄漏凭据 |
| D2 | **OCR 后端抽象**（`OcrBackend` 协议）：`LocalDdddocrBackend`（现状）/ `RemoteVisionBackend`（走 API） | 接缝只有 1 处；GUI、CLI、未来 Router 全部复用同一认证引擎 |
| D3 | **协议用 URL 路径版本**（`/api/v1`），不兼容变更出 `/api/v2`，共存期 ≥ 2 个版本 | 局域网内设备升级不同步，必须允许新旧客户端并存 |
| D4 | **配对用一次性 PIN 换 device_token**，之后 Bearer 认证；token 可在 Router 上吊销 | 不依赖公网 CA/PKI；LAN 内足够；吊销能力对应"设备丢失"场景 |
| D5 | **图像不落盘、不持久化**：验证码图片在 Router 内存中转，任务结束即丢弃 | 验证码有时效性（通常 1~2 分钟失效），落盘只有 NAND 磨损和泄漏风险，没有价值 |
| D6 | **任务结果幂等**：提交携带任务创建时下发的 `nonce`，重复提交返回 409 | 网络重试是常态，幂等是必须的 |
| D7 | **每节点同时最多 1 个任务**（由长轮询语义保证），全局 pending 上限 = 门户 `max_retry`（8） | 认证重试天然是串行的，多任务并发只会浪费节点资源 |
| D8 | **Router 端日志写 tmpfs（/tmp），不写 flash** | NAND 擦写寿命有限；现有 `logging_setup.py` 的轮转机制改为输出到 tmpfs，重启即清 |

## 4. 通信与发现

- **传输**：HTTP（明文）+ Bearer token。**不做 HTTPS**——局域网内自签证书的信任分发成本高于收益，token 泄漏风险通过配对吊销缓解。设计上留 `TLS` 扩展位（D3 的 v2 可加）。
- **服务发现**：mDNS（`_campuslink._tcp`）广播 Router 地址；失败则手动输入 IP。Desktop/Mobile 均实现双路径。
- **无公网依赖**：全部端点监听 LAN；Router 不向外发起任何与本系统相关的连接（Portal 请求除外，那是认证本身）。

## 5. Vision Lite 的诚实结论（MT7621A）

这是任务书要求"研究可能性"的部分，结论要实事求是：

| 方案 | 可行性 | 原因 |
|---|---|---|
| 现有栈（ddddocr + onnxruntime + opencv） | **不可行** | onnxruntime 无 mipsel 官方构建；RAM 预算：模型 13 MB + 推理峰值 ~60 MB + opencv ~40 MB，叠加 OpenWrt 自身 ~40 MB，128 MB 必然 OOM；MIPS 无 NEON，推理耗时不可接受 |
| 交叉编译 onnxruntime 到 mipsel | **不推荐** | 社区无维护构建，自行交叉编译 + 调 MIPS 浮点问题的成本远超收益 |
| 纯经典 CV（阈值→连通域→模板匹配） | **有条件可行，优先级最低** | 该验证码为 4 位字母数字、干扰线少（旧版实测 `color` 策略思路有效）；但需采集标注逐字符模板库，对旋转/扭曲鲁棒性差，识别率难以保证；收益仅是"无视觉节点时也能自动登录" |
| **推荐**：Router 只做编排，视觉下沉 | ✅ | Desktop/Mobile 的算力做 OCR 绰绰有余；Router 挂了 Desktop 自动降级；实现成本最低 |

**Vision Lite 定位改为"预研课题"**：路线图里排在最后（Phase 4），先交付纯经典 CV 的可行性原型（采集 200 张样本 → 切分 → 模板匹配 → 统计识别率），**识别率 ≥ 95% 才立项**，否则放弃。这个阈值写死在验收标准里，避免无限投入。

## 6. 合规边界（写死在架构里，不是口号）

任务书要求"不设计规避学校认证政策的功能"，落到设计上是这几条硬约束：

1. **单账号**：Router 托管模式使用用户自己的账号，配置里只有一个账号（沿用现有 `AppConfig` 结构），不做多账号轮换。
2. **不规避并发限制**：门户对单账号有并发终端数上限（实测会遇到"并发超限"错误）。遇到时**如实把错误报给用户**（现有 `friendly_error` 已覆盖），不做任何绕过。
3. **不做身份伪装**：不伪造 MAC、不轮换设备指纹、不模拟多终端。
4. **不共享**：配对机制只允许用户自己的设备接入；PIN 是分发手段不是分享手段（文档与 UI 都要写明）。
5. **Router 模式的性质**：本质是"把登录动作从 PC 搬到 Router 这一台设备上"，认证主体仍是用户本人账号。若学校政策明确禁止路由器级认证，**用户应停用 Router 模式**——文档中明示这一点，且 Desktop 的独立模式永远保留。

## 7. 不做什么（本阶段）

- 不安装任何依赖（含 Router 端的 Python 环境）
- 不修改 `CampusLink/` 下的任何 Windows 代码
- 不实现 API、不起草实现骨架
- 不假设门户行为变化（所有对门户的判断均基于 2026-10 的实测记录）
