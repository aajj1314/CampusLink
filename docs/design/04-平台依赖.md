# 04 · 各平台依赖关系

## 1. 依赖总览

| 平台 | 语言/运行时 | 复用现有代码 | 新增依赖 | 体积量级 |
|---|---|---|---|---|
| Desktop | Python 3.13 + PySide6 | core 全部、GUI 全部 | 无新三方库（HTTP 服务用标准库或既有 requests 系） | 安装包 ~160 MB（现状） |
| Router | Python 3 (mipsel) | `core/portal.py`、`core/netdetect.py`、`core/authenticator.py`（改 1 处）、`core/models.py`、`logging_setup.py` | 无深度学习栈 | ~15 MB flash / ~35 MB RAM |
| Mobile | Kotlin (Android 8+) | 算法思想复用，代码重写 | opencv-android、onnxruntime-mobile、OkHttp | APK 增量 ~55 MB |
| Vision Lite | C（OpenWrt 交叉编译） | 仅算法思路 | 无 | 目标 ≤ 15 MB |

**关键复用证据**（来自 00 文档的实测）：`cv2`/`numpy` 只被 `core/ocr.py` 引用，
所以 Router 只要不含 `ocr.py` 就**完全不依赖 opencv/numpy/ddddocr**——
这就是解耦价值的直接兑现。

## 2. Router 依赖与资源预算（小米 AC2100）

设备事实（OpenWrt ToH 实测数据）：MT7621A 双核 880 MHz（mipsel_24kc）、128 MB DDR3、
128 MB NAND、**无 USB**、OpenWrt 官方支持 21.02.0 起（当前 25.12.2）。

### flash 预算

| 项 | 占用 | 说明 |
|---|---|---|
| OpenWrt 基础系统 | ~10 MB | squashfs 只读分区 |
| 内核 + 内核分区冗余 | ~8 MB | 双 kernel 分区结构 |
| python3-light | ~4.5 MB | 解释器 + 基础库 |
| python3-logging / email / json / urllib | ~3 MB | requests 的依赖链 |
| python3-lxml | ~2.5 MB | mipsel 包，bs4 解析后端 |
| requests（vendored 或 pip 到 overlay） | ~1 MB | 纯 Python |
| CampusLink Router 代码 + 档案 | ~0.5 MB | 纯 Python |
| **overlay 剩余（关键指标）** | **~40–60 MB** | 需装机实测确认；低于 25 MB 则须裁剪 |

> 风险：requests / bs4 不是 OpenWrt 官方 feed 包，需要 pip 到 overlay 或 vendor 进代码树。
> 设计倾向 **vendor**（把这几个纯 Python 包直接放进源码树），避免在设备上跑 pip
> （pip 需要 python3-pip ~6 MB 且联网安装易踩 mipsel 轮子缺失）。
> lxml 是 C 扩展，必须用 feed 包；若 feed 缺失，bs4 退回 `html.parser`（慢但可用，
> 本门户页面仅 ~5 KB，性能无碍）。

### RAM 预算（128 MB）

| 项 | 峰值 |
|---|---|
| OpenWrt 内核 + 基础服务 | ~35 MB |
| wireless 驱动（mt76 全开） | ~15 MB |
| Python 进程（解释器 + 库 + 会话） | ~12 MB |
| 任务队列 + 图像缓冲（≤8 张 × ~2 KB） | < 0.1 MB |
| **余量** | **~65 MB** |

结论：**跑认证编排绰绰有余；跑视觉（任何方案）都不可行**——这是 00 文档 §5 结论的资源依据。

### 持久化与 NAND

- 日志、任务队列、图像全部走 tmpfs（决策 D5/D8）
- 写 flash 的只有：配置变更、配对/吊销设备、门户档案更新——均为低频人工操作
- `overlay_free_mb` 进入 `/system/status`，低于 10 MB 时 API 返回告警字段

## 3. Desktop 依赖

| 依赖 | 用途 | 状态 |
|---|---|---|
| 现有 requirements.txt 全部 | 现状 | 不变 |
| 视觉节点 HTTP 客户端 | 走 `requests`（已有） | **零新增** |
| mDNS 发现 | `zeroconf`（可选，~1 MB） | 设计倾向：加；若不接受新依赖则手输 IP |

> 特意不加 Web 框架：Desktop 是**客户端**角色，不提供 HTTP 服务（避免 Windows 防火墙弹窗和攻击面）。

## 4. Mobile 依赖

| 依赖 | 用途 | 体积 |
|---|---|---|
| Kotlin + OkHttp | API 客户端、长轮询 | ~3 MB |
| opencv-android | 图像预处理（复用 4 策略） | ~40 MB（按 ABI 拆分后 ~12 MB/arm64） |
| onnxruntime-mobile | 跑同一 `common_old.onnx`（13 MB） | ~15 MB |
| Android Keystore | 存 device_token | 系统 |

- minSdk 26（Android 8.0），覆盖主流设备
- 模型文件与 Desktop **同源同版本**：模型升级时两端一起换，用 `capabilities` 里的 `model_hash` 协商
- 人工输入路径**不依赖**任何 CV 库——这是 Mobile 的保底价值，APK 可以做成"轻量版（无 CV）/ 完整版"两个 flavor

## 5. 依赖治理

1. **协议优先于实现**：任何端改动都不影响其它端，只要遵守 02 文档
2. **模型即契约**：ONNX 模型的 hash 进入 `/capabilities`，版本漂移可检测
3. **Router 不引第三方服务端框架**：标准库 + asyncio 足够（端点少、并发低），减少 mipsel 依赖面
4. **Windows 稳定版零新增依赖**：视觉节点功能只允许用已有库实现，否则宁可不做
